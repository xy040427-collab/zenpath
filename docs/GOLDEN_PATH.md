# 择境 ZENPATH — AI 开发黄金路径

> 本文档定义了本项目的标准 AI 辅助开发流程。
> 每一步都有明确的目的，不允许跳过。

---

## 黄金路径总览

```
Spec → Issue → Branch → Plan → Implement → Build → Test → PR → CI → Playwright → Report → Review → Merge
```

```
┌──────────┐    ┌──────────┐    ┌──────────┐    ┌──────────┐
│   Spec   │───▶│  Issue   │───▶│  Branch  │───▶│   Plan   │
│  规格定义 │    │  任务单   │    │ 分支隔离  │    │ 执行计划  │
└──────────┘    └──────────┘    └──────────┘    └──────────┘
                                                      │
┌──────────┐    ┌──────────┐    ┌──────────┐    ┌─────▼────┐
│  Report  │◀───│Playwright│◀───│    CI    │◀───│ Implement│
│  执行报告 │    │ 页面验收  │    │ 自动构建  │    │ 代码实现  │
└──────────┘    └──────────┘    └──────────┘    └──────────┘
     │
┌────▼─────┐    ┌──────────┐    ┌──────────┐
│  Review  │───▶│  Merge   │    │  Build   │

└──────────┘    └──────────┘    └──────────┘
```

## 各步骤详解

### 1. Spec（规格定义）

**文件**：`specs/<feature>/requirements.md`

**目的**：在写任何代码之前，明确"做什么"和"不做什么"。

**必须包含**：
- 功能名称和背景
- 用户故事
- 必须实现的功能点
- 明确不做的功能（Out of Scope）
- 允许修改的文件范围
- 禁止修改的文件范围
- 验收标准
- 风险和回滚方式

**为什么需要**：没有 Spec 的开发 = 没有目标的航行。AI Agent 尤其需要明确边界，否则会自动扩大范围。

---

### 2. Issue（任务单）

**文件**：`.github/ISSUE_TEMPLATE/ai_agent_task.md`

**目的**：把 Spec 转化为可执行的任务单，明确 Agent 的具体指令。

**必须包含**：
- 任务背景和目标
- 必须实现什么
- 不做什么
- 允许修改的文件清单
- 禁止修改的文件清单
- 验收标准和测试命令

**为什么需要**：Issue 是 Agent 的"工作指令书"。没有 Issue，Agent 不知道从哪里开始、到哪里结束。

---

### 3. Branch（分支隔离）

**命令**：`git checkout -b feature/<feature-name>`

**目的**：在独立分支上工作，不影响 main 分支。

**规则**：
- 每个任务一个分支
- 分支名语义化：`feature/chat-improvement`、`fix/report-crash`
- 不允许在 main 上直接修改

**为什么需要**：分支是安全网。如果改坏了，main 还是好的。

---

### 4. Plan（执行计划）

**产出**：Agent 输出的执行计划（文本）

**目的**：Agent 先分析、后动手，让用户确认方向正确。

**必须包含**：
- 修改目标
- 允许修改的文件和原因
- 禁止修改的文件
- 执行步骤
- 预期风险
- 验证方式

**为什么需要**：Agent 的计划可能有偏差。先确认再执行，避免改错方向后返工。

---

### 5. Implement（代码实现）

**目的**：按计划小范围修改代码。

**规则**：
- 只改计划中的文件
- 每次改一个明确问题
- 不做大范围重构
- 不引入无关变更
- 发现计划外问题 → 停止并报告

**为什么需要**：小范围修改 = 小风险 = 容易 review = 容易回滚。

---

### 6. Build（本地构建）

**命令**：`cd frontend && npm run build`

**目的**：确保代码能编译通过，无类型错误。

**规则**：
- build 失败 = 任务未完成
- 不允许跳过
- 不允许为了通过 build 删除代码

**为什么需要**：build 是最低质量门槛。不能编译的代码不能合并。

---

### 7. Test（测试）

**当前状态**：尚未配置正式测试框架。

**最低要求**：
- 前端：build 通过
- 后端：uvicorn 启动成功
- 页面：核心页面无白屏

**未来目标**：
- 单元测试（vitest / pytest）
- E2E 测试（Playwright）

**为什么需要**：测试是"代码做了我说的事"的证明。

---

### 8. PR（Pull Request）

**模板**：`.github/pull_request_template.md`

**目的**：把变更打包为可审查的单元。

**必须包含**：
- 修改目标
- 修改文件清单
- 核心变更说明
- 测试结果
- 风险和未完成项

**为什么需要**：PR 是人类和 Agent 之间的"交接点"。人类通过 PR 理解 Agent 做了什么。

---

### 9. CI（持续集成）

**配置**：`.github/workflows/ci.yml`

**目的**：自动运行 build、lint、test，作为合并前的质量门禁。

**检查项**：
- checkout 代码
- 安装依赖
- 运行 build
- 运行 lint（如有）
- 运行 test（如有）

**为什么需要**：CI 是自动化的质量守门员。人类 review 可能遗漏，CI 不会。

---

### 10. Playwright（页面验收）

**配置**：`playwright.config.ts` + `e2e/`

**目的**：自动验证页面能正常打开、核心功能可交互。

**检查项**：
- 首页可打开，无白屏
- 核心导航可点击
- 关键按钮可交互
- 路由跳转正常

**为什么需要**：build 通过不代表页面正常。Playwright 验证的是"用户实际看到的"。

---

### 11. Report（执行报告）

**模板**：`docs/REPORT_TEMPLATE.md`

**目的**：Agent 记录本次执行的完整信息，供人类审查。

**必须包含**：
- 修改文件清单
- 命令运行结果
- 页面验收结果
- 安全检查结果
- 风险和未完成项
- 是否建议合并

**为什么需要**：报告是 Agent 的"工作日志"。没有报告，人类无法判断 Agent 是否真的完成了。

---

### 12. Review（人工审查）

**目的**：人类检查 Agent 的工作质量。

**检查重点**：
- 代码逻辑是否正确
- 是否修改了禁止范围的文件
- 是否有安全风险
- 是否有 mock 冒充
- UI 是否符合设计规范

**为什么需要**：AI 可能犯人类不会犯的错误。人工 review 是最后防线。

---

### 13. Merge / Reject（合并或拒绝）

**合并条件**：
- 所有检查通过
- 人工 review 通过
- 无未解决的风险

**拒绝条件**：
- build 失败
- 页面异常
- 修改了禁止文件
- 有安全风险
- 有 mock 冒充

**为什么需要**：合并是质量的最终裁决。不满足条件的代码不能进入主线。

---

## 总结

黄金路径的核心思想：

1. **先想清楚再动手**（Spec → Plan）
2. **小步快跑**（Branch → Implement）
3. **自动验证**（Build → Test → CI → Playwright）
4. **人工把关**（Report → Review → Merge）

每一步都是为了**降低风险、提高质量、保护主线**。
